# Technical decisions

A record of how the project is built and why. Game design decisions are in [`feature-registry.md`](feature-registry.md); this file is for engineering.

## How to add a decision

Add a row at the end of the right table with the next number. Give the decision, the reason, what it rules out and where it came from. A decision is changed by a new entry that names the one it replaces; old entries are not deleted.

Status values: **In force**, **Proposed**, **Replaced by TD-n**.

## 1. Decisions in force

Decisions TD-1 to TD-9 were made before this record existed. They are reconstructed from the code, the merged pull requests and the existing documents, as audited on 2026-11-12.

| # | Decision | Reason | Rules out | Source |
| --- | --- | --- | --- | --- |
| TD-1 | Two layers, Simulation and Presentation, in separate assemblies. Simulation sets `noEngineReferences` | Simulation can be tested without the engine and reasoned about without the screen | `MonoBehaviour`, `Vector3` from Unity, `Time`, `Debug` in Simulation | PR #17, `CLAUDE.md` |
| TD-2 | One interface, `IPlanetSimulation`, between the layers | Presentation work can proceed against a stand-in; the boundary is visible in one file | Views reaching into simulation classes | Issue #4, PR #17 |
| TD-3 | SI units, except time in hours and energy in Wh. `double` everywhere in Simulation. Radians in code, degrees in files and on screen | Colony time scales are hours and days; Wh matches how energy is quoted | Mixed units inside Simulation | `docs/simulation-interface.md` |
| TD-4 | The simulation advances in fixed sub-steps of at most 0.25 h | Results do not depend on frame rate or game speed | Passing frame time straight into models | `StubPlanetSimulation.Tick` |
| TD-5 | Scenes are built by `MainSceneSetup`. Scene and prefab files are never edited as text. Files are moved and renamed inside Unity; `.meta` files are committed | Several people and sessions work at once; text edits to scenes break them | Hand-wired scene objects that the setup script does not know | `CLAUDE.md`, `CONTRIBUTING.md` |
| TD-6 | All UI uses UI Toolkit | One UI system; layouts are text and merge cleanly | uGUI canvases | PR #31, #34 |
| TD-7 | One save object, `SimulationState`, versioned by an integer, serialised with `JsonUtility` by Presentation. Older versions load with defaults | Simple, readable saves; Simulation stays free of serialisation code | Binary saves; Simulation reading files | PR #37 |
| TD-8 | Planet data is generated by a tool from the NASA Exoplanet Archive plus a hand-edited input, with a provenance label on every value | Reproducible data; the game can show what is measured and what is assumed | Editing the generated file or the `PlanetDNA` assets | PR #16, #43 |
| TD-9 | The solar model has a Python prototype that is checked against pvlib and generates the C# reference values | An independent reference for the central model | Changing the C# formulas alone | PR #2, `CLAUDE.md` |
| TD-10 | The robot code lives in namespace `Robots`, not `Workforce` | The class `Workforce` would clash with a namespace of the same name | — | `docs/design/robotic-workforce.md` §9 |
| TD-11 | Every change reaches `main` through a pull request | Shared history between people and sessions | Direct pushes to `main` | `CONTRIBUTING.md` |

Decisions made with the architecture foundation of 2026-11-12:

| # | Decision | Reason | Rules out | Status |
| --- | --- | --- | --- | --- |
| TD-12 | No new assemblies for now. Structure inside Simulation is by namespace and tier | The project has 128 source files; more assemblies would add ceremony and are blocked by namespace cycles anyway | Per-category assemblies (data, persistence, infrastructure) | In force |
| TD-13 | Colony systems exchange values through the orchestrator and hold no references to each other | The pattern the code already follows; keeps systems testable alone | Service locators, global event buses, systems calling systems | In force |
| TD-14 | New documents are in English, in `docs/<area>/` with lowercase hyphenated names. Existing Thai documents stay as they are. `CLAUDE.md` stays in Thai | English matches the code, the comments and `docs/design/`; the lowercase names match every existing file. The director may overrule (OQ-6) | Renaming or translating existing documents without a decision | In force |
| TD-15 | A .NET project, `tools/simtests`, compiles and runs the simulation tests without Unity | Sessions without the editor can check their work; it makes continuous integration possible. Unity's Test Runner stays authoritative | Treating a pass outside Unity as final | In force |
| TD-16 | Enums that appear in saved games are append-only | `JsonUtility` stores them as integers | Reordering, inserting or deleting members | In force |
| TD-17 | Feature status is tracked in `feature-registry.md` with separate design and implementation columns | Planned and built were being confused across documents | Status lines scattered through specifications as the only record | In force |

## 3. Never decided

Found in the project with no record of a choice. They work today; each becomes a decision when it starts to cost something.

| Matter | State | When to decide |
| --- | --- | --- |
| Render pipeline | Built-in pipeline with hand-written shaders | Before investing in visual effects or targeting other platforms |
| Input | Legacy `Input` class, keys hard-coded in views | Before adding key rebinding or controller support |
| The Unity MCP package tracks its `main` branch | An unpinned dependency in `Packages/manifest.json` | Before a release build; pin a version |
| Localisation | UI text is English strings in code and UXML; documents are partly Thai | Before a second UI language |
| Save location and slots | One file, `kardashev-save.json` | With several colonies or planets |
| Target platforms | A Windows build menu exists | Before platform-specific work |
| Simulation threading | Single-threaded; only `PreviewPanel` is called from a worker thread | With the performance budget of stage H |
